# Bounded retained-router protocol diagnostic

The September 12 replacement-key STORY request reached the outer JSON-envelope
guard after the transport and JSON checks. Its body was not retained before
settlement failed. Its exact fields and status cannot be reconstructed. The two
old unknown reservations and this third unknown remain occupied; normal reviews
remain blocked.

An explicit server operator may admit one different, tiny protocol diagnostic
under the original root. The request is fixed: the existing `route-llm` endpoint,
a boolean JSON schema, 32 output tokens, no image, audio or tools. It is not a
retry of the production STORY request. Its response can describe only this probe;
it cannot establish what the lost STORY body contained or approve video quality.

Admission verifies the completed failure proof binding, the exact fifteen
existing records, archived/current replacement key, source, runtime revision,
original entitlement window and enforced zero-cash policy. The operator validates
the actual private failure file and tested deployment; the application checks
the supplied hash and live record bindings without claiming to read that file.
All five production feature flags remain false. No window, account funding,
source or old request record is initialized, changed or renewed.

Three permanent probe records are created in one watched transaction before a
private, one-use, thread-bound send permit exists. Exact acknowledgement and
readback are required. The three previous occupied unknowns plus this probe count
as four requests within the existing six-request aggregate. Any probe record,
including a partial one, also terminally fences normal reserve paths. It never
reopens STORY, visual, ASR or prosody calls. Independent permanent operator
attempt evidence prevents automatic resubmission after an uncertain SSH result.

The diagnostic transport accepts only that closed permit and fixed request. It
uses one HTTPX request with retries, redirects, ambient proxies and provider
fallback disabled. Before any semantic observer, it captures the actual status,
bounded response bytes, original prepared body and verified outgoing wire body.
Non-success statuses and invalid JSON are retained too. A truncated or interrupted
body is explicitly marked incomplete; it does not receive a complete-body claim.

The response and body identities are encrypted with a separate domain derived
from the existing application encryption key. Request/response headers are not
stored. Full encrypted evidence is retained in the three durable private Redis
records; no S3 acknowledgement or bucket-privacy claim is made. Hashes and exact
readback protect those records. A lost write acknowledgement leaves the request
occupied and exposes only an issuer-bound encrypted fallback to the original
operator, without permitting another send. Post-request key/source/window drift
does not erase this diagnostic evidence or authorize further work.

The public summary contains fixed statuses, booleans, counts and only allowlisted
field names with their types. Arbitrary provider strings, field names, headers
and plaintext response bytes never enter logs, errors or Redis. Every receipt
remains diagnostic-only with QA, publication, resume and retry authority false.
Local zero-cash allowance is not a verified provider invoice or account balance.

The fixture tests use real Redis transactions and actual HTTPX mock transport to
check source races, partial records, lost acknowledgements, copied/thread-moved
permits, single-send behavior, encrypted credential echoes, bounded partial reads
and immutable record validation. They do not assert real provider compatibility.
Coordinated loss of all independent records remains an operator reconciliation
case, never an automatic commissioning path.
